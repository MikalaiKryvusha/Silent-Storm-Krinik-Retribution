# Silent-Storm-Krinik-Retribution — техническое задание: стек и план переноса Silent Storm в WebGPU

**Статус:** проект технической концепции  
**Целевая платформа:** браузер (приоритет), Android как дополнительная цель  
**Основной принцип:** игровая логика не должна знать, на какой ОС, устройстве или графическом API она работает.

## 1. Цель проекта

Создать современную платформенную оболочку и графический backend для Silent Storm, максимально сохранив и повторно используя существующий C/C++-код, игровые алгоритмы, Lua-скрипты и форматы данных.

Игра должна запускаться по ссылке в браузере. Основной графический API — **WebGPU**. Игровая логика, AI, тактическая симуляция, баллистика и большая часть игрового движка должны оставаться на C++ и собираться в **WebAssembly (WASM)**.

Это не перенос игры на новый универсальный движок и не переписывание проекта на JavaScript. Это последовательная модернизация существующего движка через платформенные и графические адаптеры.

### Приоритеты

1. Максимально сохранить исходный C/C++-код и упростить его дальнейшую поддержку.
2. Изолировать платформозависимые вызовы от игровой логики.
3. Минимизировать объём переписывания и количество специальных изменений в старом коде.
4. Получить браузерную сборку на WebAssembly + WebGPU.
5. Сохранить возможность собирать тот же игровой код для Android и других нативных платформ.
6. Обеспечить постепенную модернизацию графики без необходимости переписывать игровую симуляцию.
7. Сохранять проверяемое соответствие игрового поведения оригинальной Silent Storm.

## 2. Исходная база: два проекта GitHub

### 2.1. `met-nikita/Silent-Storm-Reconstruction`

https://github.com/met-nikita/Silent-Storm-Reconstruction

Это реконструкция исходников Silent Storm с целью получить версию, поведение которой соответствует релизу v1.2. Автор использует PDB-файлы v1.1 и декомпиляцию v1.2. Репозиторий собирается через CMake, но его текущая сборка ориентирована на Windows Win32/x86.

**Роль в Krinik:** основной источник восстановленной игровой логики и поведения версии 1.2. Использовать как целевую версию игровых систем после проверки совместимости с платформенными адаптерами.

### 2.2. `timskap/silent-storm-port`

https://github.com/timskap/silent-storm-port/tree/android-port

Это практическая работа по переносу движка на Android. В ветке `android-port` также находится каталог `reconstruction/`, куда импортировано дерево `met-nikita/Silent-Storm-Reconstruction` с сохранением истории и фиксацией конкретной ревизии.

В проекте уже реализованы важные для Krinik подходы:

- современная сборка старого C++-кода через Clang/Android NDK, CMake и Ninja;
- отдельный слой совместимости Win32/POSIX/Android;
- staging-скрипт, который копирует исходники в генерируемое дерево и применяет документированные исправления, не изменяя оригинальные файлы;
- загрузка оригинальных `.res`, `game.db`, текстур и выполнение Lua 4.0;
- Android-ввод, файловая система и платформенная оболочка;
- графический backend `d3d9gles`, реализующий интерфейс `NGfx` поверх GLES 3.0.

**Важное ограничение текущего состояния:** Android-сборка в этой ветке пока использует исходный движок из январского снимка 2003 года через `prepare_sources.py`. Каталог `reconstruction/` импортирован отдельно; его более поздние изменения ещё не стали автоматически основой Android runtime. Для перехода на него нужна отдельная адаптация и проверка.

### 2.3. Принятая стратегия использования

- `Silent-Storm-Reconstruction` — целевой источник восстановленного поведения v1.2.
- `silent-storm-port` — практическая основа для платформенной абстракции, staging-процесса, Android-адаптации, тестового harness и изучения графического интерфейса `NGfx`.
- Оригинальный код и импортированные деревья сохраняются отдельно и не редактируются напрямую без необходимости.
- Нельзя считать, что обе кодовые базы уже полностью совместимы: переход Android-порта на реконструированную версию и создание WebAssembly-сборки являются отдельными инженерными задачами.

## 3. Принцип архитектуры

Игровая логика должна зависеть только от внутренних интерфейсов движка. Она не должна напрямую обращаться к Win32, Android NDK, DOM, JavaScript, WebGPU, GLES или конкретной файловой системе.

```text
                    KRINIK GAME CORE
        C++: gameplay · AI · Lua · ballistics · simulation
                              |
                 Internal Engine Interfaces
                    /                    \
                   /                      \
          Platform Abstraction          NGfx / Render Interface
             (PAL)                             |
       /       |       \                /     |      \
    Windows  Android   Web          Legacy  GLES   WebGPU
                                  (reference) (Android) (browser)
                                                |
                                      Browser WebGPU API
```

### Правило №1: не переписывать игровой код ради платформы

Сначала добавлять адаптер или совместимый слой. Изменения в игровом ядре допускаются только там, где обнаружены реальные платформенные предположения, ошибки 32/64-bit, undefined behavior или архитектурные ограничения, которые невозможно устранить снаружи.

### Правило №2: оригинальные исходники не патчить вручную без необходимости

Продолжить подход `prepare_sources.py`:

1. Исходное дерево хранится неизменным.
2. Скрипт подготовки формирует рабочее дерево для конкретной платформы и версии исходников.
3. Каждое преобразование оформляется отдельным именованным правилом.
4. Правила документируются, привязываются к исходной ревизии и проверяются автоматически.
5. Генератор должен уметь выводить полный отчёт обо всех применённых изменениях.

Это позволит обновлять исходники Reconstruction и не терять платформенные исправления.

### Правило №3: симуляция отделена от визуализации

Результат выстрела, попадания, пробития, повреждения или разрушения вычисляет игровой C++-код. GPU отвечает за изображение и визуальные эффекты. Игровой результат не должен зависеть от того, работает ли рендерер на WebGPU или GLES.

## 4. Рекомендуемый технологический стек

| Область | Технология | Назначение |
|---|---|---|
| Игровое ядро | Существующий C/C++, поэтапно C++17/20 там, где требуется | Повторное использование оригинального кода |
| Скрипты | Существующая Lua 4.0 VM | Сохранение оригинальных игровых скриптов |
| Сборка | CMake + Ninja | Единая система сборки для разных targets |
| Компилятор Web | Clang из Emscripten SDK | Сборка C/C++ в браузерный WASM |
| Браузерный runtime | WebAssembly + Emscripten | Выполнение игрового ядра в браузере |
| WebGPU из C++ | EmdawnWebGPU (`webgpu.h`) | Доступ C/C++ к WebGPU API браузера |
| Графический интерфейс движка | Существующий `NGfx` | Стабильная граница между движком и backend |
| Новый renderer | `NGfx-WebGPU` | Реализация рендеринга через WebGPU |
| Android renderer | Существующий GLES backend | Сохранение Android-направления |
| Платформенная абстракция | Собственный PAL/compat layer на основе Android-порта | Время, файлы, потоки, ввод, звук, пути, диагностика |
| Веб-оболочка | Минимальный HTML + JavaScript/TypeScript | Canvas, запуск WASM, браузерные события и API |
| Хранение в браузере | Emscripten FS на первом этапе; далее IndexedDB/VFS | Сохранения и локальный кэш ресурсов |
| Офлайн-запуск | PWA + Service Worker | Кэширование загрузчика и игровых ресурсов |
| Тестирование | Существующий native test harness + CTest; Playwright для браузера | Регрессии логики, загрузки и пользовательских сценариев |

### Почему нужен WebAssembly

WASM не является обязательным для самого WebGPU, но для этого проекта он является правильным способом запускать существующий C/C++-код в браузере. Вместо переписывания десятков и сотен тысяч строк на JavaScript, C++ компилируется в WASM и выполняется внутри браузера.

JavaScript используется как тонкая оболочка для интеграции с браузером. Не следует переносить в JavaScript игровую симуляцию или делать JavaScript посредником для каждого draw call.

### Почему не Babylon.js, Three.js или React как основа движка

У Silent Storm уже есть собственный игровой цикл, сцена, рендер-контракт, ресурсы, материалы и графическая логика. Подключение ещё одного полноценного 3D-движка создаст второй набор сцен, ресурсов и систем синхронизации.

Для максимального повторного использования C++ и производительности предпочтительнее реализовать WebGPU backend непосредственно за существующим интерфейсом `NGfx`. HTML/TypeScript оставить для браузерной оболочки, загрузки, PWA и вспомогательного интерфейса.

## 5. Графическая стратегия: NGfx → WebGPU

Android-порт уже документирует границу, за которой графическая реализация отделяется от остального движка. Согласно `android/docs/RENDERER.md`, backend должен реализовать графические операции за `NGfx`; остальная часть `Main` взаимодействует с этим контрактом.

**Предлагаемое решение:** создать отдельную реализацию `NGfx-WebGPU`, не переписывая игровой код и не ломая существующий GLES backend.

### Этап A — функциональное соответствие

Сначала WebGPU backend должен воспроизводить существующую графику, а не улучшать её:

- жизненный цикл графического устройства и swap chain;
- vertex/index buffers и динамическую загрузку геометрии;
- текстуры и все используемые игровые форматы;
- texture atlases и существующую адресацию UV;
- render targets, cube maps и depth/stencil;
- blend, depth, stencil, culling и color-write state;
- существующие эффекты и shader-пары;
- screenshot/readback для тестирования.

WebGPU — API с явными pipeline state, bind groups и command encoders, поэтому старую модель D3D9 нельзя механически перенести вызов-вызов. Нужно реализовать соответствие семантики старого `NGfx` современным объектам и состояниям WebGPU, с кэшированием pipeline и ресурсов.

### Этап B — шейдеры

В документации Android renderer отмечено, что исходные D3D9 shader blobs содержат `DBUG`-блоки с исходным assembly-текстом. Сначала извлечь и сохранить эти тексты в репозитории.

Далее:

1. Составить каталог всех используемых shader/effect-пар.
2. Использовать существующий GLES-порт как эталон понимания поведения шейдеров.
3. Перенести исходную математику и поведение в WGSL.
4. Сравнить результаты на одних и тех же сценах и материалах.
5. Добавить автоматические снимки/сравнение изображений для регрессий.

Не считать, что есть универсальный конвертер, который без потерь переведёт все D3D9 shader model 1.x в WGSL. Нужен поэтапный перенос с проверкой особенностей старых инструкций и эффектов.

### Этап C — постепенное улучшение изображения

После достижения визуального соответствия можно независимо улучшать renderer:

- качество и точность освещения;
- тени и их разрешение;
- материалы и normal mapping;
- постобработку и цветокоррекцию;
- эффекты дыма, огня, частиц и атмосферы;
- сглаживание, anisotropic filtering и mip management;
- LOD, динамическое разрешение и масштабирование качества;
- дополнительные визуальные эффекты разрушения.

Каждое улучшение должно быть опциональным и иметь профиль качества. Оно не должно менять игровые правила или требовать изменения AI/тактической симуляции.

## 6. Платформенная абстракция (PAL)

Постепенно изолировать следующие сервисы за внутренними интерфейсами:

- **File System / VFS:** нормализация Windows-путей, регистронезависимый поиск, `.res`, `game.db`, конфигурации, сохранения.
- **Asset Loading:** загрузка ресурсов из локальной папки, браузерного кэша или по HTTP; в дальнейшем — потоковая подгрузка.
- **Input:** клавиатура, мышь, touch, жесты, gamepad.
- **Audio:** отдельный backend для Web Audio; не привязывать игровой код к FMOD.
- **Time:** единый монотонный источник времени и управляемый игровой timestep.
- **Threading:** сначала однопоточный WebAssembly runtime; позже — Web Workers и SharedArrayBuffer при наличии cross-origin isolation.
- **Window / Surface:** создание canvas и управление размером viewport без передачи DOM-объектов в игровое ядро.
- **Diagnostics:** единые логи, assert, профилирование и сбор отчётов.

На первом браузерном прототипе допустимо использовать Emscripten FS и загружать ограниченный набор ресурсов вместе с билдом. Затем перейти к VFS с асинхронной загрузкой и IndexedDB-кэшем, чтобы не упаковывать всю игру в один огромный initial download.

## 7. Совместимость браузеров и fallback

Основной браузерный backend — WebGPU. Однако требование «работать в любом браузере» нельзя гарантировать одним WebGPU: поддержка зависит от браузера, ОС, GPU и доступных функций.

Поэтому:

1. При запуске проверять наличие WebGPU и необходимые capabilities.
2. Если WebGPU доступен — запускать `NGfx-WebGPU`.
3. Если WebGPU недоступен — показывать понятное сообщение на первом этапе.
4. В дальнейшем оценить отдельный WebGL2 fallback. Существующий GLES backend может стать полезной отправной точкой, но его перенос в WebGL2 тоже потребует проверки и адаптации.

**Целевой принцип:** WebGPU-first, а не WebGPU-only навсегда. Это позволит сохранить высокое качество и производительность на современных браузерах, не закрывая путь к более широкой совместимости.

**Результат:** воспроизводимые исходные сборки и документированная карта расхождений.

- Сохранить исходники неизменными, все необходимые исправления оформить staging-правилами.

**Результат:** игровое ядро собирается с платформенными адаптерами без ручного редактирования исходного дерева.

### Фаза 2. WebAssembly bring-up

- Получить первую страницу, запускающую C++-код в браузере.

**Результат:** браузер действительно выполняет код движка, но полноценный 3D ещё не обязателен.

### Фаза 3. WebGPU backend

- Реализовать инициализацию WebGPU через EmdawnWebGPU.

**Результат:** оригинальная геометрия и материалы отображаются через WebGPU.

### Фаза 4. Вертикальный срез игры

- Загрузить оригинальную тестовую карту и игровые ресурсы.

### Фаза 5. Интеграция Reconstruction v1.2

**Результат:** браузерный runtime использует выбранную восстановленную игровую базу, а не только исходный снимок 2003 года.

### Фаза 6. Полноценная графика и ресурсы

### Фаза 7. Оптимизация и дополнительные платформы

- Профилировать C++ CPU-код, WASM, GPU и передачу данных.

**Результат:** один код игрового ядра, несколько платформенных сборок и контролируемые профили производительности.

## 9. Критерии готовности

- Игровая симуляция не содержит прямых зависимостей от браузера, Android или графического API.
- Исходное дерево не модифицируется скрытыми ручными патчами; все преобразования воспроизводимы.
- C++ и Lua 4.0 выполняются в WebAssembly.
- WebGPU backend реализует существующий `NGfx`-контракт либо документированную совместимую его эволюцию.
- Тестовая карта отображается с оригинальными моделями и текстурами.
- Основные игровые действия воспроизводимы и не зависят от рендерера.
- Есть тесты загрузки ресурсов, Lua, сохранений, тактической логики и графических регрессий.
- Браузер корректно определяет отсутствие WebGPU и не падает молча.
- Android и Web builds используют общие игровые модули.
- Производительность измеряется на заранее выбранных ПК и Android-устройствах; цели FPS и памяти фиксируются после первого рабочего прототипа, а не назначаются вслепую.

## 10. Риски и ограничения

1. **Реконструкция и Android-порт пока не являются одной готовой кодовой базой.** Ветка `android-port` содержит Reconstruction как отдельное импортированное дерево, но Android runtime использует более ранний исходный снимок. Интеграция требует отдельной работы.
2. **D3D9 → WebGPU — не механическая замена API.** Необходимо корректно воспроизвести старые состояния рендеринга, render targets, stencil, форматы текстур и shader model 1.x.
3. **WebGPU пока не поддерживается одинаково всеми браузерами и устройствами.** Нужны runtime capability checks и, возможно, WebGL2 fallback.
4. **WASM имеет ограничения браузерной среды.** Потоки требуют дополнительных условий безопасности сайта; доступ к файлам и ресурсам должен идти через VFS/браузерные механизмы.
5. **Лицензия.** Официальный репозиторий Nival указывает специальную лицензию, запрещающую коммерческое использование. До публичного или коммерческого релиза требуется отдельная юридическая проверка исходников, игровых данных, торговых марок и сторонних компонентов.
6. **Производительность нельзя выводить из одной цифры FPS Android-прототипа.** Нужны отдельные измерения CPU, GPU, WASM и загрузки ресурсов на целевых устройствах.

## Краткое итоговое решение

**Не переносить Silent Storm на другой игровой движок. Сохранить C++-ядро и существующий `NGfx`, создать WebAssembly-сборку через Emscripten, реализовать отдельный WebGPU backend через EmdawnWebGPU и развивать платформенную абстракцию на базе подходов `silent-storm-port`.**

В качестве целевого игрового поведения использовать `Silent-Storm-Reconstruction` v1.2, интегрируя его изменения в платформенные сборки постепенно и с регрессионными проверками. Сначала добиться функционального соответствия оригиналу, затем улучшать графику поэтапно — независимо от игровой логики.
